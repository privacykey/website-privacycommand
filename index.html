The gap

Permissions tell you what an app can do. Not what it does.

macOS shows you the prompts. The App Store shows you what a developer says they collect. Neither tells you what's inside the binary you just installed, like the hard-coded analytics endpoints, the embedded ad SDK, the launch agent that survives reboots, the file paths the app touches the moment you open it.

privacycommand reads what's there: static signals from the bundle, live signals from a real run, and the developer's declared Privacy Manifest cross-checked against both. You get one report in plain English, exportable as JSON, HTML, or PDF.

Built into the same drop

Everything you'd reach for, in one window.

Watch an app live

Network destinations, file events, child processes, and resource usage all stream into one view. A heat-graded callout fires the moment something spikes, such as a burst of disk writes, a fresh outbound host, or a CPU climb that wasn't there a second ago.

Check an update before it lands

Drop in a candidate update and diff it against the version on disk. For Sparkle-distributed apps, privacycommand reads the appcast itself and pulls the next release straight into the inspector, so the audit happens before the live app's auto-updater ever sees it. The History tab does the same for any two saved reports: added and removed entitlements, domains, SDKs and login items are colour-cued, with a show-only-changes toggle.

Links to common tools

Every finding shows the underlying command (codesign, otool, plutil, fs_usage, sfltool, lsof, mdls), copy-able with one click. Quick-launch into Suspicious Package, Hopper, or your own preferred tool when you want to dig deeper.

VM mode

For apps you'd rather not run on bare metal, ship a guest agent into a macOS VM (VirtualBuddy, UTM, Parallels) and stream observations back to the host across the VM boundary. Same analyzer, isolated host.

Telemetry callout

Heat-graded count of analytics, advertising, and attribution SDKs in the bundle, with the per-category breakdown and the matched Mach-O strings behind every detection. Hover any SDK to see exactly what fingerprinted it.

Codesign & notarisation

Full chain validation: Developer ID, Team ID, hardened-runtime flags, stapled notarization ticket, SHA-256 of the bundle, spctl assessment. Every relaxation flagged with the entitlement key behind it.

Batch scan a whole fleet

Point privacycommand at a folder, or all of /Applications, and triage every app at once in a sortable, filterable table: risk tier, warning and error counts, and the headline signals for each. The same analyzer runs on every bundle. One click opens any row in the main window for the full deep-dive.

Decompile the call site

The binary summary maps every function that can open a connection (BSD sockets, getaddrinfo, CFNetwork, Network.framework) with any host or URL literal sitting beside it. Decompile any call site on demand if you have Ghidra installed. For relaunchable apps without hardened runtime, capture a live call stack that ties a real outbound connection back to the function that opened it.

Claims vs. binary

When the bundle came from the Mac App Store, privacycommand pulls the developer's declared Privacy Nutrition Labels from Apple and sets them beside its own static-analysis findings, so you can see for yourself whether what they say they collect matches what the binary reaches for.

FAQ

The questions that come up first.

Is privacycommand really free?

Yes, it's free and open-source under the MIT licence, with no accounts, subscriptions, or upsells. The full source is on GitHub for anyone to read or fork.

Does privacycommand need admin / root access?

Not for the core report: static analysis, App Store privacy-label cross-check, and the Background Task Management audit all run unprivileged. The optional helper unlocks live file-event monitoring (fs_usage) and the network kill switch (pf anchor). Installing it asks for admin once, after which it stays out of your way.

Does privacycommand send anything anywhere?

All analysis runs locally, and the app makes only three explicit, bounded network calls: DNS reverse lookups for destinations the inspected app contacts (so the Network tab can label 8.8.8.8 as dns.google), Mac App Store privacy-label lookups against itunes.apple.com keyed on the inspected app's bundle ID, and the Sparkle appcast fetch when you check for updates. The inspected app's contents never leave your machine.

Is it a malware sandbox?

Not exactly, because privacycommand is a forensic auditor that tells you what an app contains and what it does on a normal run. For risky apps you'd rather not run on bare metal, VM mode lets you ship the same analysis into a macOS VM (VirtualBuddy, UTM, Parallels) and stream observations back. It's adjacent to a sandbox; it's optimised for transparency rather than detonation.

Apple Silicon, Intel, both?

Both, because the DMG is a universal binary signed and notarized for macOS 13 (Ventura) and later. The Homebrew cask resolves to the same artefact.

What kinds of apps can I drop on it?

Any .app bundle, plus .dmg installers, which privacycommand will mount to inspect the bundle inside. Mac App Store apps, Developer ID apps, Catalyst, Electron, Tauri, Java-on-mac wrappers, and command-line apps wrapped as .app all parse. Apps without a bundle (raw command-line binaries) are out of scope today.

What does it find that I couldn't find by hand?

The same things you could find with codesign, otool, plutil, fs_usage, sfltool, and a stack of grep, except cross-referenced and explained. The difference is consistency: privacycommand runs every detector against every drop, in the same shape, and explains every finding in plain English so the report is shareable with someone who isn't a binary-analysis nerd.

Can I export reports for a ticket or a vendor review?

Yes, every audit exports as JSON, HTML, or PDF. The HTML and PDF exports are designed to read like an IT vendor-review one-pager; the JSON keeps every detector's raw output for downstream tooling.

Install

Pick the way that fits your fleet.

All three install the same signed, notarized binary. Pick whichever fits how you already manage Mac software.

Recommended

Homebrew tap

The way most teams already install Mac software. brew upgrade --cask privacycommand keeps it current; privacycommand notices it's running from a Homebrew Caskroom and disables in-app updates so brew stays in charge.

$ brew install privacykey/tap/privacycommand

Signed DMG

The signed and notarized .dmg from the latest GitHub release. Drag the app into /Applications, you're done. In-app updates ship via Sparkle 2. Auto-checks are off by default, and you opt in via Settings → Updates.

Build from source

Open the Xcode project or build the SPM target directly. The pure-Swift analyzer is AppKit-free, so you can drive it from the CLI (auditctl) or wrap it in your own tooling.

$ git clone github.com/privacykey/privacycommand
$ cd privacycommand/privacycommand
$ swift build
